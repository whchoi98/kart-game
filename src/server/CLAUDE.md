# Server Module

## Role
Fastify 5 HTTP server. It owns the time-trial leaderboard API, server-side re-simulation of every submitted run on a worker-thread pool, the `/healthz` probe, static hosting of the built client (`dist/client`) with SPA fallback, security headers and per-viewer rate limits. Development runs the TypeScript source through `tsx` (`npm run dev`); the container runs the esbuild bundle `dist/server/index.js` plus `dist/server/verify-worker.js` built by `tools/build.mjs`.

Routes (all registered in `app.ts`):
- `GET /healthz` -> 200 `{ ok: true, version }`. Pure liveness: never touches DynamoDB or the verifier, exempt from rate limits, successful probes are not logged. Used by the ALB target group, the ECS container health check and the Dockerfile `HEALTHCHECK`.
- `GET /api/leaderboard?track=<trackId>&cc=<50|100|150|200>` -> top 50 (`API_LIMITS.leaderboardSize`). Both parameters required, no others; `cc` is a string enum here.
- `GET /api/ghost/:id` -> one ghost log. `id` must match `RUN_ID_PATTERN`, no query allowed, 404 once a faster run replaced it, `cache-control: private, max-age=3600, immutable`.
- `POST /api/runs` -> 9 required fields, no extras (`submitRunSchema`): integer `cc`, `ticks` 1..108000, 1..9 `lapTicks`, `log` 1..200000 chars matching `^[A-Za-z0-9+/_=-]+$`, `name` 1..64 in the schema and 1..12 after `normalizeName`. Order: rate limit (429) -> `originGuard` (403) -> `jsonOnly` (415) -> body and schema (413/400) -> name (400) -> verify (503) -> `compareResult` (422) -> `repository.submit` (409) -> 200 `{ accepted, id, rank, personalBest }`.

## Key Files
- `app.ts` - `buildApp(options)`: Fastify options, global hooks, error handler, compression, rate limits, routes, SPA not-found handler, `DEFAULT_RATE_LIMITS`, `compareResult()`.
- `index.ts` - entry point: `readConfig()`, pino logger (`LOG_LEVEL`), production warnings, SIGTERM/SIGINT drain with a 25 s deadline (ECS `stopTimeout` is 30 s), `listen`.
- `config.ts` - `readConfig(env)` parses and validates the environment; `builtVersion()` reads `dist/build.json`.
- `errors.ts` - `ApiFailure` and the public error factories: the only codes and (Korean) messages that cross the HTTP boundary.
- `validation.ts` - request and response JSON schemas, `BODY_LIMIT` (256 KiB), `MAX_RUN_TICKS`, `MAX_LAPS`, `RUN_ID_PATTERN`, `normalizeName`, `newRunId`, `logDigest`.
- `security.ts` - `SECURITY_HEADERS`, `clientKey` (rate-limit key), `normalizeAddress`, `isOriginAllowed`, `isJsonContentType`.
- `static.ts` - `@fastify/static` registration, cache constants, `sendIndex`, `isSpaNavigation`.
- `verifier.ts`, `verify-worker.ts` - `WorkerVerifier` pool and its worker, which runs `verifyTimeTrial` from `src/sim/replay.ts`. `ts-worker-bootstrap.mjs` loads the `.ts` worker through tsx in development only.
- `repository.ts` - `Repository` contract, `VerifiedRun`, `DuplicateRunError`, key builders. Implementations: `memory-repository.ts` (process-local) and `dynamo-repository.ts` (single table, `StorageError`, `createDocumentClient`).

## Rules
- Error codes: 400 `INVALID_REQUEST`/`INVALID_NAME`, 403 `FORBIDDEN_ORIGIN`, 404 `NOT_FOUND`, 409 `DUPLICATE_RUN`, 413 `PAYLOAD_TOO_LARGE`, 414 `INVALID_REQUEST` (route parameter over 100 characters, API-only server; see Gotchas), 415 `UNSUPPORTED_MEDIA_TYPE`, 416 `RANGE_NOT_SATISFIABLE`, 422 `VERSION_MISMATCH`/`REPLAY_INVALID`/`TIME_MISMATCH`/`LAP_MISMATCH`, 429 `RATE_LIMITED`, 503 `VERIFIER_BUSY` (Retry-After 3) or `SERVICE_UNAVAILABLE` (Retry-After 2). Error bodies are `{ error, message }`; 422/409 bodies are `SubmitRunResponse` plus `error` and `message`.
- Public errors come only from `errors.ts` factories (plus the 414 and generic-4xx `ApiFailure`s and the 422/409 bodies built in `app.ts`). Anything unrecognised becomes 503 `SERVICE_UNAVAILABLE`; the `request_failed` log keeps only the route template, the error name, a stable `code` and the `reason` of `StorageError`/`VerifierUnavailableError`. Never log or return query strings, bodies, names, IPs, `playerId` or exception messages (`runs.test.ts` checks for leaks).
- Response schemas in `validation.ts` are allow-lists (`additionalProperties: false`): a field missing from the schema is silently dropped from 200 responses, and `playerId` must never be added to one.
- Adding a route: register it inside the `try` block of `buildApp` before `registerStatic`; give it `onRequest: [readLimit]` (or its own limiter) and add its URL to `SELF_LIMITED_ROUTES`, otherwise the global hook charges it a second time; use `noQuerySchema` when it takes no query; declare a response schema; put shared types in `src/shared/api.ts`. On POST routes keep the limiter before `originGuard` and `jsonOnly` so malformed floods are still charged.
- Adding a rejection code: extend `RunRejectionCode` in `src/shared/api.ts`, `compareResult()` here and `CODE_MESSAGES` in `src/client/api.ts` together.
- `VERSION_MISMATCH` is returned only when the replay fails and the semver core (text before `+`) of the submitted `version` differs from the server version; a run from another build that still verifies is accepted. Trajectory-changing edits in `src/sim/` therefore need a `package.json` version bump.
- Rate limits (`DEFAULT_RATE_LIMITS`, 60 s window): submit 12 (`POST /api/runs`), read 120 (leaderboard, ghost and unmatched `/api/*`), page 600 (pages, static files, other 404s); `/healthz` is exempt. Not configurable by environment, only through `BuildAppOptions.rateLimits`. The store is in-process, so each Fargate task counts separately.
- Rate-limit key (`clientKey`): the `x-turbo-client-ip` header when it holds a valid IP, else the socket address (`trustProxy: false`; behind the ALB that is the ALB's private IP). The CloudFront viewer-request function (`VIEWER_IP_FUNCTION_CODE` in `infra/lib/edge.ts`) overwrites the header with the viewer IP. IPv4-mapped addresses collapse to IPv4, IPv6 to its /64. Use it for rate limiting only; never log or store it.
- Origin allow-list (`isOriginAllowed`): a request without `Origin` passes (non-browser clients rely on replay verification); otherwise the origin must exactly match `PUBLIC_ORIGIN` or an `ALLOWED_ORIGINS` entry, or be same-host when both are empty. In ECS, `infra/lib/stack.ts` sets `PUBLIC_ORIGIN` to the site origin and, with a custom domain, `ALLOWED_ORIGINS` to the native CloudFront domain.
- Security headers: `SECURITY_HEADERS` (CSP, nosniff, frame DENY, no-referrer, Permissions-Policy, COOP/CORP same-origin) go on every response, including router-level errors. Change values only in `src/shared/csp.ts`, which the CloudFront response headers policy shares. HSTS and `upgrade-insecure-requests` are added at the edge only, because the origin also serves plain HTTP locally.
- Caching: files under `assets/` get `public, max-age=31536000, immutable`; every other static file (index.html, `sw.js`, the manifest, `build.json`, icons) gets `no-cache`; API responses and every status >= 400 get `no-store`. The SPA fallback serves index.html only to GET/HEAD paths outside `/api`, `/healthz` and `/assets/` whose last segment has no dot, so a missing asset stays a JSON 404 and HTML is never cached as a script.
- Config (`readConfig`): `NODE_ENV` (`production` switches defaults), `PORT` (8080), `HOST` (`0.0.0.0` in production, else `127.0.0.1`; an IP or `localhost`), `APP_VERSION` (default `<version>+<id first 12>` from `dist/build.json`, then `package.json`), `TABLE_NAME` (empty -> memory repository), `STATIC_DIR` (`dist/client`), `PUBLIC_ORIGIN`, `ALLOWED_ORIGINS` (comma separated exact `scheme://host[:port]`, at most 16 combined), `AWS_REGION` or `AWS_DEFAULT_REGION`; `index.ts` reads `LOG_LEVEL`. A new variable also goes into `.env.example`, the container environment (`infra/lib/service.ts` or `infra/lib/stack.ts`) and `validation.test.ts`.
- In production the server refuses to start without `index.html` in `STATIC_DIR`, and warns (`memory_repository`, `no_public_origin`) when `TABLE_NAME` or the origin list is empty.
- Verifier (`WorkerVerifier`): `min(2, availableParallelism())` workers (1..8 allowed), warmed at startup; 8 s CPU budget per run (an overrun terminates the worker and rejects the run with 422, not 503); 32 queued runs and a 6 s queue wait, beyond which `VERIFIER_BUSY`; worker crash, load failure or malformed reply -> 503 `SERVICE_UNAVAILABLE`; worker heap 256/32 MB; reasons truncated to 200 chars. Keep the queue wait below the browser's 8 s `API_TIMEOUT_MS` (`src/client/api.ts`). `defaultWorkerUrl()` expects the bundle name `verify-worker.js` produced by `tools/build.mjs`.
- Repository semantics (both implementations): one row per player per track+cc board; a run that is not faster, or carries the same `logHash`, returns the existing best (`personalBest` is true only for the identical retry); a `logHash` already claimed by another player throws `DuplicateRunError` (claims are permanent); rank is 1-based among other players and null outside the top 50; ties sort by the time-ordered run id.
- DynamoDB single table (`pk`/`sk` strings, no GSI): `LB#<track>#<cc>` / `<ticks padded to 9>#<runId>` ranking row (never the log), `PB#<track>#<cc>#<playerId>` / `PB` best pointer, `GHOST#<runId>` / `GHOST` ghost log (outside the board partition), `LOG#<logHash>` / `LOG` log claim. Reads are consistent GetItem/Query; a new best is one `TransactWriteItems` (4 Puts, plus 2 Deletes when replacing), up to 5 attempts on transaction conflicts. The task role allows only GetItem, PutItem, DeleteItem and Query on the table ARN: a new access pattern (UpdateItem, Scan, a GSI) also changes `infra/lib/service.ts`, `infra/lib/data.ts` and `test/infra/stack.test.ts`. `tools/verify-live.ts` deletes its QA rows with these key builders.
- `MemoryRepository`: at most 5000 stored runs (503 for a new player beyond that), log claims capped at 50000 (oldest dropped); keep mutations synchronous so the concurrency rules match DynamoDB.
- Update together: endpoint, payload, limit or error-code changes -> `src/shared/api.ts`, `src/client/api.ts`, `docs/api-reference.md`, `docs/reference/api.md`; key schema or access patterns -> `docs/reference/data.md` and this file; `security.ts` -> `docs/reference/security.md`.

## Testing
- `npx vitest run test/server`. `test/server/helpers.ts` provides `testApp()` (MemoryRepository, `stubVerifier`, `staticDir: false`, rate limits 10000), `submit()`, `runBody()` and `clientFixture()` (a temporary built client).
- `http`, `rate-limit`, `runs` and `validation` tests cover routes, headers, limits and config; `verifier.test.ts` drives the pool with `test/server/fixtures/scripted-worker.mjs` and `broken-worker.mjs`; `replay.integration.test.ts` re-simulates a real CPU-driven log through the `.ts` worker.
- `repository.test.ts` runs `repositoryContract` against memory always and against DynamoDB Local only when `DYNAMODB_TEST_ENDPOINT` is set (loopback hosts only): `docker run -p 18765:8000 amazon/dynamodb-local`, then `DYNAMODB_TEST_ENDPOINT=http://127.0.0.1:18765 npx vitest run test/server/repository.test.ts`.

## Gotchas
- `/healthz` stays 200 while DynamoDB is down; there is no readiness endpoint.
- With a built client, `@fastify/static` registers a `/*` wildcard route: a request that misses an API route (e.g. a ghost id over Fastify's 100-character `maxParamLength`) falls through to it and gets a JSON 404 charged to the read budget, not the router's 414. `testApp()` runs API-only (`staticDir: false`), so cover static-dependent behaviour with `clientFixture()`.
- `keepAliveTimeout` (65 s) must stay above the ALB idle timeout (60 s).
- Schema `MAX_RUN_TICKS` (108000) is wider than the sim's `MAX_TT_TICKS` (43380): runs in between pass validation and fail replay with 422.
- `logDigest` hashes the decoded input sequence, so re-encoded ghosts collide on purpose; changing `src/sim/input-log.ts` can break that equivalence.
