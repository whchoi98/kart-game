# Tracks Module

## Role
- Authored track data for the deterministic simulation: one `TrackDef` per file (control points, edges, surfaces, pads, ramps, movers, scenery hints) plus the lightweight menu catalog. `../track-builder.ts` turns a def into a `BuiltTrack`; nothing here runs per tick.
- Track geometry is time-trial physics: editing a physics field of an existing track invalidates stored replays and requires a `package.json` version bump (see "Version bump" in `../CLAUDE.md`); adding a new track does not.

## Key Files
- `catalog.ts` - `TRACK_CATALOG` (`id`, `name`, `nameEn`, `cup`, `order`, `theme`, `blurb`; no geometry, so menus never build a track), `CUPS` (`sprout`, `thunder`: names, color, emblem), `tracksOfCup(cup)` sorted by `order`, `getTrackMeta(id)` (throws on an unknown id).
- `index.ts` - imports every def into the private `ALL` array; `TRACK_DEFS` is the catalog order filtered to defs present in `ALL`; `hasTrackDef`, `getTrackDef`.
- Track defs, all `laps: 3`: Sprout Cup `sunny-meadow.ts` (theme `meadow`), `palm-beach.ts` (`beach`), `canyon-rally.ts` (`canyon`), `neon-city.ts` (`city`); Thunder Cup `frost-peak.ts` (`snow`), `jungle-ruins.ts` (`jungle`), `lava-fortress.ts` (`volcano`), `starlight-road.ts` (`galaxy`). `sunny-meadow.ts` scales control-point x and z by `S = 1.25`.

## Rules
- The catalog decides which tracks exist and in which order. `TRACK_DEFS`, the server's `TRACK_IDS` (`src/server/validation.ts`: the `trackId`/`track` enum of `POST /api/runs` and `GET /api/leaderboard`), course select, leaderboard tabs, saved-menu validation (`src/client/ui/memory.ts`), the Grand Prix (`tracksOfCup`, every track of the cup) and the QA tools all read `TRACK_CATALOG`.
- Mismatches fail quietly: a def missing from the catalog disappears from the game and from `test/sim`; a catalog entry without a def passes the server schema, but replays fail with `unknown track` and `getBuiltTrack` throws.
- Keep `id`, `name`, `nameEn`, `cup`, `order` and `theme` identical in the def and its catalog entry; nothing checks it. Menus read `meta.theme`, the race reads `track.def.theme`.
- Physics fields: `points`, `halfWidth`, `shoulder`, `defaultEdge`, `startAt`, `laps`, `edges`, `surfaces`, `boostPads`, `ramps`, `movers`. `itemRows` and `coins` matter only outside time trials. `name`, `nameEn`, `theme`, `music`, `scenerySeed`, `parLap`, `landmarks` and the catalog `blurb` never reach the physics.
- `music` is required by the type but no code reads it: the race song is looked up by track id in `TRACK_SONGS` (`src/client/audio/songs/index.ts`) and an unknown id silently falls back to the menu theme. Keep `music.bpm`/`key` in line with the song (`SPEC` in `test/client/audio-songs.test.ts` pins each song's bpm and key). `parLap` is an authoring note; no UI shows it.
- `u` coordinates: every `at`, `from` and `to` is a control-point index plus a fraction (`u = 3.5` is halfway between points 3 and 4 in spline parameter, not in metres) and wraps modulo the point count; ranges may wrap past 0. Inserting or removing a control point shifts every later `u`, so re-check all positions after it.
- Control-point order is the driving direction. `startAt` is the start/finish line; the 8-slot grid sits behind it (`s = startS - 7 - 4.2 * k`, alternating sides, slot 0 = pole).
- Lateral values: `d` in metres, positive to the right of travel; `side` is relative to travel. `ControlPoint.w` overrides `halfWidth`; `bank` > 0 lowers the right side; width and bank are smoothstep-interpolated between points.
- Edges: `offroad` (dirt shoulder of `shoulder` m, overridable per `EdgeRange`, then a barrier), `wall` (barrier at half width + 0.6 m), `pit` (no barrier; a kart that leaves the road falls and respawns). `defaultEdge` applies wherever no `EdgeRange` does. Surfaces: `dirt` and `mud` cap grounded speed at 0.55 and 0.42 of max (not while boosting or under a star), `ice` keeps speed but cuts grip; `dFrom`/`dTo` limit a zone to a lateral band, and the first matching zone wins.
- Movers: `sweep` oscillates laterally around `d` at a fixed `at` (`amplitude` m, `period` s per oscillation, `phase` rad); `travel` drives along the loop from `at` (`period` s per lap, `phase` as a lap fraction). Positions are a pure function of the world tick (countdown included) and stay on the road deck (never up a ramp).
- Mover `look`: in the sim it picks the hit (`HARD_LOOKS` in `../race.ts` tumble, other looks spin) and the capsule half-length (`MOVER_HALF_LENGTH`: bus, truck, car). A new look also needs a model from the theme's `createMover` and a decision on the client's roll list (`HARD_LOOKS` in `src/client/game/race-session.ts`).
- Landmarks are render hints only: `kind` is theme specific, `side` is `left`/`right`/`over`, `dist` is metres from the centreline. `grandstand`, `arch` and `banner` are drawn by the track mesh (`isTrackMeshKind` in `src/client/render/themes/props-a.ts`), every other kind by the theme's scenery builder.
- Mirror mode (`mirrorDef` in `../track-builder.ts`; time trials never mirror) negates control-point x and `bank`, swaps edge and landmark sides, negates and swaps surface `dFrom`/`dTo`, and negates `d` of boost pads, coins and movers; ramps and item rows stay unchanged. Author only the normal direction, and extend `mirrorDef` whenever you add a lateral or side field to `TrackDef`.

## How to add a track
1. Create `<id>.ts` exporting a `TrackDef`. Required: `id`, `name`, `nameEn`, `cup`, `order`, `theme`, `laps` (use 3), `halfWidth`, `shoulder`, `defaultEdge`, `points` (at least 4), `startAt`, `music`, `scenerySeed`. Optional: `edges`, `surfaces`, `boostPads`, `itemRows`, `coins`, `ramps`, `movers`, `landmarks`, `parLap`.
2. `index.ts`: import it and add it to `ALL`.
3. `catalog.ts`: add the matching `TRACK_CATALOG` entry with a Korean `blurb`. The server enum, menus, leaderboard and Grand Prix pick it up with no server change; adding it to an existing cup lengthens that Grand Prix.
4. New cup only: `CupId` in `../types.ts`, `CUPS`, and `CUP_IDS` in `src/client/storage.ts` (trophies; the mirror unlock needs 150cc gold in every cup).
5. Theme: reuse an existing `ThemeId`, or add one following `src/client/render/themes/CLAUDE.md` (`npm run typecheck` lists every `Record<ThemeId, ...>` to fill).
6. Music: add `src/client/audio/songs/<id>.ts` with `id: '<id>'` and list it in `TRACK_SONGS` (`src/client/audio/songs/CLAUDE.md`).
7. Validate geometry: `npx tsx tools/track-report.ts <id>` (SVG plan in `test-results/tracks/`, exit code 1 on a problem in the normal or mirror build). Problems: corner radius below half width + 2 m, slope above 16 degrees, two road sections closer than their half widths + 2 m with under 7 m height difference, a grid slot, item box or boost pad off the road, a ramp starting within 30 m after or 45 m before the start line. A lap outside 700-1900 m is only a warning.
8. Validate driving: `npx tsx tools/sim-report.ts <id>` must show all 8 CPUs finishing (no `(est)`) and `verify={"ok":true,...}` for the bot time trial.
9. Tests: `npx vitest run test/sim test/client/audio-songs.test.ts test/client/audio-system.test.ts`. `test/sim/sim.test.ts` covers the new def automatically (it assumes 3 laps); update the track count (8) and `SPEC` in `audio-songs.test.ts` and the cue list in `audio-system.test.ts`. Then `npm run typecheck`.
10. Look at it: `npm run dev`, then `npm run qa:screens -- --tracks <id>` against it. Update the track table in `docs/design.md` (section 6).
11. Version: a new track changes no existing replay, so the replay rule does not force a `package.json` bump; note that any bump makes clients discard queued offline runs recorded under the old semver core (`dropStalePendingRuns` in `src/client/storage.ts`). Editing a physics field of an existing track does require the bump.
